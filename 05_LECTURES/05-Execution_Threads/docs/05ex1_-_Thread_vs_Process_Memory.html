Address sharing, atomicity and visibility

This page serialises callbacks in one JavaScript event loop. It is a sequential illustration of shared storage, not a native thread test. In C/POSIX, counter++ is not automatically atomic: protect reads and writes with the same mutex, or use C atomics with appropriate ordering. For example, an unlock followed by a successful lock of the same mutex establishes the required ordering. Each thread can address shared storage, but that alone does not guarantee a defined instantaneous observation. See the race-condition and mutex lessons.

Threads share code, data, heap and file descriptors. Each thread has its own stack, registers, thread-local storage and per-thread attributes. Creation costs depend on implementation and workload; no native timings are measured here.

Demonstration: Shared Variable Behaviour

Scenario 1: Threads

1. Global variable: counter = 0

2. Thread 1 executes counter++

3. Thread 2 sees the new value after synchronisation.

Sequential illustration: all callbacks access the same stored value.

Scenario 2: Processes

1. Global variable: counter = 0

2. fork() → child modifies counter

3. Parent does NOT see the change!

Separate private copies of this variable; explicit shared mappings have different semantics.
