Overlay model and Dockerfile scope

Lookup, read and merged view use the same per-path upper state. Deleting a copied-up lower file removes the upper copy and adds a whiteout; recreating it removes that whiteout. Storage is a qualitative count of upper entries, not invented MB. The corrected Dockerfile fragment installs Python and a virtual environment, copies requirements.txt before installing it, then copies app/. It groups multiple actual layers for this display. Supply requirements.txt and app/ in the build context and choose the application entry point; these project inputs and a container build are not supplied or executed here.

The OverlayFS Model

OverlayFS combines lower and upper directories into one merged view. The lower directories are read-only in this model; container modifications are represented in the writable upper directory.

Container sees a single file hierarchy, but data comes from different layers!

Dockerfile → logical layer groups

FROM ubuntu:22.04 # Group 1: base image layers
RUN apt-get update && apt-get install -y --no-install-recommends python3 python3-venv && python3 -m venv /opt/venv # Group 2: system tools
COPY requirements.txt /tmp/requirements.txt
RUN /opt/venv/bin/python -m pip install --no-cache-dir -r /tmp/requirements.txt # Group 3: COPY and RUN layers
COPY app/ /app # Group 4: application files

RUN and COPY generally add filesystem layers; each displayed group may contain more than one actual image layer. Supply requirements.txt and app/ in the build context. The application entry point must be specified separately.

Best Practices

  • Fewer layers: Combine RUN commands
  • Order matters: Put changing things at the end (cache!)
  • No secrets: Don't store credentials in layers

Layer Sharing Efficiency

Containers using the same local image can share its read-only layers, reducing duplicated image storage.
